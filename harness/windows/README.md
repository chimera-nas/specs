# Windows SMB server conformance harness

Replays the generated SMB2 corpus (`quint/smb2`) against the Windows SMB
server itself, on Windows Server 2025 and on Windows 11, and compares every
reply to the result the model baked into the trace.

The Samba suite ([`../samba/`](../samba/)) tests the model against an
implementation nobody consulted while writing it. This one asks the more
pointed question. Windows is the implementation MS-SMB2 and MS-FSA *describe*,
so where the model and Windows disagree, the model's reading of the documents
is the first suspect.

It is the same replayer — `../samba/smb2_replay.py`, a raw SMB2 client, not
the Windows redirector — and the same flavours and batches as the Samba cells.
The two servers are asked exactly the same questions.

## Where an implementation differs is in its config, and nowhere else

Every difference between Windows and the model's defaults is a branch **in the
model**, and the setting that selects it is in `configs/_windows.json`. The
harness forgives nothing: `windows_deviations.py`, the registry the replayer
consults about a reply that does not match, is empty and is meant to stay that
way.

There are two kinds of setting, and the distinction is the point:

* A **policy** is a place where implementations of the same documents are
  found doing different things, each defensibly. The model carries both arms as
  a named constant and each implementation's config says which it takes.
* A **deviation** is a place where the implementation gets the standard
  wrong. It has an id, a citation, and a strict twin that turns it off.

Everything found against Windows so far is a policy. That is not a courtesy to
Windows: a behaviour of the reference implementation is evidence about what
the documents mean, and filing it as a fault would be the model marking its own
homework.

## Running

It runs on a Windows machine, elevated, and it **changes that machine's SMB
server configuration** — an account, a share, leasing off, the Server service
restarted — and does not put it back. Run it on a disposable machine. In CI
that is the `windows` job of `.github/workflows/build.yml`, on the
`windows-2025` and `windows-11-arm` runners.

```
python -m pip install smbprotocol==1.17.0
./harness/windows/run_windows_mbt.ps1 -CorpusRoot <corpus root> [-Cells stepCore,stepInfo] [-Survey]
```

`<corpus root>` is the directory holding `windows/smb2/<cell>/*.itf.json`. The
corpus is generated by this project's ordinary Linux build (the cells are
registered in `CMakeLists.txt`); nothing on the Windows side needs quint or
cmake, only Python and the replay client. CI generates it once in the `build`
job and hands the same bytes to every replay job.

The server is the in-box one. The script gives it a share over a fresh NTFS
directory, a local account with full control of that directory, and turns
leasing off. The replayer empties the share between traces itself.

`-Survey` reports every diverging step of a trace instead of stopping at the
first; `-ReportOnly <cells>` runs the named cells in that mode and keeps their
result out of the exit status.

## What Windows does differently

Measured identically on Windows Server 2025 (10.0.26100, x64) and Windows 11
(10.0.26200, ARM64): the two produced the same replies to all 46 traces.

### Policies

| policy | default | Windows | Samba |
|--------|---------|---------|-------|
| `lockAccessCheck` | `true`: a LOCK through a handle with neither `FILE_READ_DATA` nor `FILE_WRITE_DATA` is refused `STATUS_ACCESS_DENIED` | `false`: no such check — the lock is granted, a conflict is `LOCK_NOT_GRANTED`, an unlock of a range not held is `RANGE_NOT_LOCKED` | `true` |
| `supersedeWantsDelete` | `false`: a `FILE_SUPERSEDE` of an existing file arbitrates for WRITE, like `FILE_OVERWRITE` | `true`: it arbitrates for DELETE — admitted past a holder that does not share write, refused by one that does not share delete | `false` |
| `createTypeFirst` | `false`: `FILE_CREATE` + `FILE_NON_DIRECTORY_FILE` onto an existing directory reports `OBJECT_NAME_COLLISION` | `true`: it reports `FILE_IS_A_DIRECTORY` | `true` |

`createTypeFirst` began as a Samba deviation (SD-5). This suite is what
retired it: Windows does the same thing.

`lockAccessCheck` deserves a second look in the other direction. The check was
added to the model on the strength of the Samba suite, and four Samba
deviations (SD-2, SD-8, SD-9, SD-13) are refinements of how Samba performs it.
Windows does not perform it at all. The model's default still does, because
changing a default changes every consumer's corpus; whether the default should
follow Windows is an open question this suite raised and did not settle.

### Deviations

None.

### What the harness had to learn

Three things the first run found were the harness's own, and are fixed in the
client rather than recorded anywhere:

* Windows refuses a `FILE_RENAME_INFORMATION` buffer shorter than 24 bytes
  with `STATUS_INFO_LENGTH_MISMATCH`, which a one-character name is. Samba
  accepts it.
* SMB2 oplocks cannot be turned off on Windows (`EnableOplocks` governs SMB1
  only), so the one flavour that puts oplock requests on the wire and relies on
  getting no grant, `stepReq`, is not registered here: the replayer has no
  break lifecycle.
* The replay client's `cryptography` dependency has no ARM64 Windows wheel, so
  the Windows 11 job runs an emulated x64 Python. Only the client is emulated.

## The cells

| cell | config | traces | status |
|------|--------|--------|--------|
| `stepCore` | `core.json` | 8 | gates |
| `stepDir`  | `dir.json` | 8 | gates |
| `stepInfo` | `info.json` | 8 | gates |
| `stepNs`   | `ns.json` | 8 | gates |
| `notifyNs` | `notify_ns.json` | 6 | gates |
| `notify`   | `notify.json` | 8 | **reports only** |

No cell has a strict twin: none enables a deviation, and a strict twin leaves
policies as set, so it would be a byte-identical second corpus.

### `notify` is open work

The namespace half of CHANGE_NOTIFY (`notifyNs`: entries appearing, being
renamed and disappearing, through the two name filters) replays against
Windows record for record.

The full flavour does not, and it is not one difference. Seven of its eight
traces diverge, in at least these ways:

* the model completes a request for an attribute, size, last-write or stream
  change that Windows never reports to that watch;
* Windows parks a request the model answers inline, and answers inline one the
  model parks, on the stream filters and on some zero-length output buffers;
* a request the model refuses `STATUS_INVALID_PARAMETER` is refused
  `STATUS_ACCESS_DENIED`;
* `STATUS_NOTIFY_ENUM_DIR` arrives where the model predicts a successful
  completion, and a successful completion where the model predicts
  `STATUS_NOTIFY_ENUM_DIR` or `STATUS_NOTIFY_CLEANUP`.

Samba diverges on this same flavour (SD-10, SD-11, SD-12), which suggests the
model's account of which operations raise which change classes is where to
look. Until that is done the cell runs in survey mode and reports without
gating, so the debt is re-measured on every run rather than hidden — and
nothing about it is forgiven in the harness.
